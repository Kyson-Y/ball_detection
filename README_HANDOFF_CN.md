# MaixCAM 钢球视觉交接与测试

本文是队友接手当前正式视觉版本时的第一入口。当前生产代码只看
[`ai_yolo_today_v3`](ai_yolo_today_v3/)，不要从仓库根目录的旧背景差分代码开始改。

## 1. 当前基线

- 正式分支：`main`
- 已验证代码基线：`0bb0fff`
- 板端模式：`yolo11_today_v3`
- 相机：`640x480 @ 60 FPS`
- 模型输入：`320x64`，模型文件为 `.mud + .cvimodel`
- 固定 ROI：`(x=0, y=176, width=640, height=128)`
- 网页预览：按需 JPEG，`480x360 @ 2 FPS`
- 实测识别与 UART：通常约 `59-60 Hz`，开启 2 FPS 预览时 11 秒实测
  `650` 帧，即 `58.94 Hz`
- 串口：UART0，`A16=TX`、`A17=RX`、`115200 8N1`
- 当前坐标：画面向右为正，临时零点为 `x=320`
- 当前换算：`0.390625 mm/px`，机械最终固定后仍需复核

H.264 和独立 60 Hz UART 的未完成实验保存在
`wip/h264-60hz-uart-20260731`，提交 `c4b0492`。该分支尚未完成带球验收，
不要直接合并或部署到正式测试车。

## 2. 方案演进：从第一次失败到最终可用

下面按实际开发顺序说明每一种方案。后续调试不要只看到最终代码就重新引入已经
验证过的问题。

### 2.1 灰度阈值、二值化和色块质心

最初利用“水管白色、钢球灰色”这个先验，将灰度图按约 `165` 的阈值二值化，
再使用 MaixPy 的连通域/色块函数寻找 blob，并以 blob 质心作为钢球位置。

这个方法速度快，也不要求目标必须是规则圆形；`find_blobs` 找的是满足阈值的连通
区域，不关心它是圆、方块还是不规则反光。但实物测试暴露了几个无法靠单一阈值
解决的问题：

- 钢球有强高光，同一个球内部会同时出现白区、灰区和黑区，二值化后被切成多个 blob；
- 阴影、曝光和水管外背景会产生大量噪点；
- 水管端部、黑色机械构件和反光也可能满足同一阈值；
- 膨胀、闭运算或强行合并 blob 后，钢球容易与水管边缘连成大区域，甚至把整条
  水管或整幅 ROI 当成一个目标；
- 阈值降低会增加目标和噪点，阈值升高又会丢掉钢球暗部，没有一个固定值能覆盖
  所有光照与位置。

因此，单纯“二值化 -> 找色块 -> 质心”只适合受控光照下的演示，不能作为车载
最终识别。这个阶段保留下来的只有两个思想：把问题限制在窄水管 ROI 内，以及最终
只需要输出沿水管方向的一维位置。

### 2.2 空管标定、一阶差分和一维投影

第二阶段先拍摄多帧空管并求平均，运行时把当前 ROI 与空管参考图逐像素作差，
再二值化变化区域。随后沿水管宽度方向压缩成一维响应，用局部窗口积分和加权质心
得到钢球横坐标。这就是之前所说的“空管一阶比较/一维差分”方案。

它比固定灰度阈值好，因为检测的是“相对空管新增了什么”，而不是猜测钢球的绝对
灰度；钢球高光被切成几块时，一维投影也有机会把它们合并成同一个峰。平放且完全
固定时，这个方案确实可以工作。

失败根因是它依赖严格像素对齐：

- 水管一倾斜或相机轻微抖动，当前管壁与空管参考错开，整条边缘都会产生差分；
- 左侧为机构变动端，端部随倾角变化最明显，所以画面最左边经常被误认成钢球；
- 水管在 ROI 内平移后，即使没有钢球，也会出现大面积“变化目标”；
- 光照、阴影和金属反射变化会被当成物体变化；
- 同一个钢球产生多个差分峰时，最大峰可能在不同帧之间切换。

所以重新标定只能修复“标定时刻”的对齐，不能解决运行中的结构运动。这个阶段保留
了空管负样本、窄 ROI、一维坐标和无效帧保护，但最终识别不再依赖空管逐像素差分。

### 2.3 动态 ROI、图像配准和规则过滤

为修复背景差分，曾尝试亮度补偿、上下平移对齐、动态 ROI、管壁/标记配准、形态学
合并、多候选筛选和物理速度门限。这些方法能缓解单一问题，但没有形成稳定的最终
方案：

- 水管变动端不是整幅图像的刚性平移，单一平移量无法同时对齐两端；
- 每帧旋转或透视配准会增加计算量，和 `60 Hz` 目标冲突；
- 配准失败时仍可能把管壁差分当成球；
- 机械结构尚未固定时，动态 ROI 会不断扩大搜索范围，把杂乱背景重新引入；
- 规则越多，光照或姿态稍有变化就需要重新调一组阈值。

最终机械结构能够固定，因此没有继续把动态 ROI 放进正式版本。这个阶段真正保留下来
的是后处理思想：多候选不能只选置信度最高者，还必须结合上一位置、速度和最大物理
跳变量判断目标连续性。

### 2.4 第一版 YOLO：方向正确，但数据不完整

随后改用 YOLO11，让模型直接学习钢球在实际水管、反光和机械背景中的外观。第一轮
采集了空管、中心球、左端球和右端球，并加入曝光和阴影增强。相对差分方法，它不再
要求当前画面和某一张空管图逐像素一致。

第一版仍不够稳定：钢球到两端时偶尔漏检，球不在管内时又可能把右端黑色构件认成
球。原因不是 YOLO 原理失效，而是训练分布不完整：

- 两端样本和运动模糊样本不足；
- 右端构件“有时可见、有时不可见”的困难负样本不足；
- 最终上车后的 ROI 和早期采集几何不完全一致；
- 自动框选的不确定帧如果未经人工复核，会把错误标签带入训练。

因此没有继续只调置信度阈值，而是在最终机械结构和最终 ROI 下重新采集、人工复核和
训练。

### 2.5 最终数据集和 `320x64` YOLO11

最终版本以今天确定的 `640x128` ROI 为准，重新采集空管、左中右静态球和约 35 秒
连续滚动序列，并对不确定帧进行网页人工标注。训练集报告包含：

- 共 `1019` 张图；
- `775` 张有球、`244` 张空管/困难负样本；
- `340` 张静态球、`437` 张运动球；
- 曝光、亮度和阴影等光度增强；
- `94` 张运动帧由人工复核。

模型采用 YOLO11n，输入为 `320x64`。ROI 与模型输入都是 `5:1`，缩放时不会改变
水管纵横比；模型经 MaixHub 转换为 `.mud + .cvimodel`，在 MaixCAM NPU 上开启
双缓冲推理。

最终 PC/ONNX 复测集合共 `598` 张，其中 `455` 张有球、`143` 张无球；在
`0.25/0.50/0.70` 三个置信度阈值下，该集合记录为 0 漏检、0 空管误检。94 张人工
复核运动帧的横坐标误差中位数约 `0.34 px`，p95 约 `1.67 px`，最大约
`3.58 px`。这些数字证明模型导出前后一致，但不等于实车环境永远不会误检，实物
连续性测试仍是最终验收标准。

### 2.6 最终运行时不是“裸 YOLO”

每帧 YOLO 输出后，正式脚本还执行以下保护：

1. 按类别、框尺寸、宽高比和画面边界过滤候选；
2. 未锁定目标时，要求相近位置连续出现 2 帧才建立目标；
3. 已锁定后，根据上一位置和速度预测本帧位置；
4. 拒绝超过最大速度、跳变余量或预测窗口的候选；
5. 多候选相互冲突时本帧输出无效，而不是强行选一个；
6. 合法位置进入 alpha-beta 滤波，连续 3 个有效测量后速度才标记有效；
7. 无候选或跳变被拒绝时发送 `DETECTED=0`，绝不把错误坐标伪装成控制输入。

最后将模型 x 坐标乘以 2 映射回 640 像素 ROI，以 `x=320` 为临时 O 点，再按
`0.390625 mm/px` 转为毫米。UART 每个完整视觉帧发送一个带 CRC 的 22 字节包。

### 2.7 为什么没有保留 H.264 图传

识别稳定后又测试了硬件 H.264/RTSP，希望同时保留高帧率识别和视频。MaixCAM 当前
相机通道调度有明显耦合：

- RTSP 配成 `15 FPS` 时，某些父子通道组合会把完整识别循环直接锁到约 `15.15 Hz`；
- `320x240@60` RTSP 有客户端观看时，识别约 `57.40 Hz`；
- 降到 `160x120@60` 后仍约 `57.86 Hz`，说明固定的逐帧编码/发送开销更关键；
- 相机请求 `65 FPS` 会切换到实际 80 FPS 模式，完整循环反而下降；
- MaixCAM 当前 `Rtsp.write()` 未实现，无法简单地让 60 Hz 识别只每 4 帧手动推送
  一帧 H.264。

因此正式版本回退到整合 H.264 之前的方案，只保留按需 `480x360 @ 2 FPS` JPEG
预览。预览在线程中编码，队列只保留最新帧；没有网页请求时停止提交预览帧。这样在
可观察性的同时，把相机和 NPU资源优先留给识别与 UART。

### 2.8 最终方案为什么能行得通

最终方案能稳定工作的原因不是某一个阈值，而是以下条件同时成立：

- **输入几何固定**：最终相机、水管和 `640x128` ROI 固定，不再要求软件追着结构跑；
- **不依赖背景像素对齐**：YOLO 学习目标外观，轻微亮度和局部背景变化不会像空管
  差分那样把整条管壁激活；
- **数据来自最终结构**：两端、运动球、空管和右端构件困难负样本都进入训练与复核；
- **模型足够小**：`320x64` 保持 ROI 比例，NPU 单次推理约 1 ms，完整循环接近
  相机的 60 FPS 上限；
- **时间连续性兜底**：YOLO 负责“看起来像不像球”，连续性门控负责“运动上是否
  可能是同一个球”；
- **无效数据不会进入控制**：CRC、flags、测量年龄和 MCU 状态机共同阻止错误坐标；
- **图传主动降级**：正式版只保留 2 FPS JPEG，不让视频吞掉控制链路预算。

当前带 2 FPS 预览的 11 秒实测为 `650` 个完整视觉/UART 周期，即 `58.94 Hz`，
状态页通常显示约 `59-60 Hz`，`uart_errors=0`。

最终方案仍有明确边界：它没有识别整条水管并动态重建坐标系，O 点仍是相机画面
`x=320`。如果相机或水管整体移动，位置零点会跟着产生偏差；因此最终安装必须固定，
并复核 `center_x_px`、`mm_per_pixel` 和方向。H.264、任意姿态水管和大范围动态 ROI
属于后续独立课题，不能算作当前版本已经解决。

每个相机帧的流程是：

```text
640x480 RGB
  -> 裁剪 640x128 水管 ROI
  -> 缩放到 320x64
  -> YOLO11 NPU 推理
  -> 尺寸、宽高比和类别过滤
  -> 多候选连续性关联与不合理跳变拒绝
  -> 映射回 640 像素 ROI
  -> 相对 O 点换算 mm
  -> alpha-beta 位置/速度滤波
  -> 生成 22 字节 CRC 包
  -> UART0 发送
```

没有候选、候选冲突或跳变不合理时，本帧发送正常格式的无效包：
`DETECTED=0`、位置和速度为 0、`age_ms=65535`。下位机不能把这个 0 当成
“球回到中心”。

## 4. 上电后的快速检查

1. 先打开风扇，再给 MaixCAM 上电。当前配置 `70 C` 告警、`75 C` 停止，
   正式测试应尽量保持在 `70 C` 以下。
2. 等待开机应用启动，打开 `http://10.5.66.1:8080/`。
3. 检查 `http://10.5.66.1:8080/status.json` 中：
   - `mode == "yolo11_today_v3"`
   - `detect_rate` 和 `data_rate` 通常为 `59-60 Hz`
   - `uart_errors == 0`
   - `preview_errors == 0`
   - `temperature_c < 70` 为理想状态
4. 空管时确认 `detected=false`、`control_valid=false`，持续观察至少 10 秒。
5. 将球依次放在左、中、右，确认 `control_valid=true`，且
   `position_mm` 左负、中间接近 0、右正。
6. 手动连续滚动钢球，检查位置连续性；单帧跳变超过 `25-30 mm` 或
   推算速度超过 `1000 mm/s` 应记录为疑似换目标。
7. 断电重启一次，确认应用仍自动启动且网页恢复。

用 PowerShell 统计 10 秒真实处理帧数：

```powershell
$a = Invoke-RestMethod http://10.5.66.1:8080/status.json
$t = [Diagnostics.Stopwatch]::StartNew()
Start-Sleep 10
$b = Invoke-RestMethod http://10.5.66.1:8080/status.json
$t.Stop()
($b.frames - $a.frames) / $t.Elapsed.TotalSeconds
```

建议验收值：10 秒不少于 `580` 个完整视觉/UART 周期，状态页瞬时值稳定在
`59-60 Hz` 附近。不要只截取某一个瞬时 `detect_rate` 数字作为结论。

## 5. UART 接收最低要求

物理连接：

```text
MaixCAM A16 / UART0_TX  ->  MSPM0 PB16 / UART2_RX
MaixCAM GND             ->  MSPM0 GND
3.3 V TTL, 115200 8N1
```

每包固定 22 字节：

| 偏移 | 字段 | 说明 |
| ---: | --- | --- |
| 0..1 | `AA 55` | 帧头 |
| 2..4 | version/type/length | 固定 `01 01 16` |
| 5 | flags | 检测、速度、标定、温度等状态 |
| 6..7 | seq | 小端 `uint16`，每包递增 |
| 8..11 | capture_time_ms | 相机采样时刻 |
| 12..13 | position | 小端 `int16`，单位 `0.1 mm` |
| 14..15 | velocity | 小端 `int16`，单位 `mm/s` |
| 16 | confidence | `0..255` |
| 18..19 | age_ms | 有效测量年龄 |
| 20..21 | CRC16 | CRC16-CCITT-FALSE |

MCU 使用位置前必须同时满足：

```c
control_valid = crc_ok
             && ((flags & 0x01u) != 0u)  /* DETECTED */
             && ((flags & 0x20u) != 0u)  /* CALIBRATION_VALID */
             && (age_ms <= 100u)
             && (rx_timeout_ms <= 100u);
```

完整字节定义、CRC 和 C 解码器见
[`ai_yolo_today_v3/README_MCU_UART_CN.md`](ai_yolo_today_v3/README_MCU_UART_CN.md)。

## 6. 推荐的 MCU 状态机

状态机应加在“UART 解包/CRC 校验”之后、“现有底盘控制算法”之前。它只决定
视觉输入能否送入控制器，不要在这个改动中重写底盘控制算法。

```text
NO_DATA -> ACQUIRING -> TRACKING -> HOLD -> LOST
    ^          |           |         |       |
    +----------+-----------+---------+-------+
```

推荐规则：

| 状态 | 进入条件 | 行为 |
| --- | --- | --- |
| `NO_DATA` | 上电或 100 ms 未收到 CRC 正确的新包 | 禁止视觉闭环 |
| `ACQUIRING` | 已收到数据，但有效包尚未连续 3 包 | 只更新诊断，不进入闭环 |
| `TRACKING` | 连续 3 包满足 `control_valid` | 将位置送入现有控制器；速度只在 bit1 有效时使用 |
| `HOLD` | `TRACKING` 后出现 1-2 个无效包，且总时长不超过 50 ms | 不使用包内的零位置；短时保持上一有效值或执行现有安全策略 |
| `LOST` | 无效持续超过 50 ms，或 100 ms 无新包 | 退出视觉闭环，进入电控定义的安全状态 |

任意状态下出现以下情况应立即禁止视觉闭环：

- CRC 错误持续出现；
- `seq` 长时间不变化；
- 接收超时超过 100 ms；
- `CALIBRATION_VALID=0`；
- MCU 二次检查发现不可能的位置跳变或速度。

不要在 `HOLD` 状态把无效包中的位置 0 送进 PID。是否短时保持上一位置，必须由
电控负责人根据机构安全性决定。

温度 bit6 仅表示板端达到 `70 C` 预警线，应记录告警并加强散热；它本身不代表
坐标无效。达到 `75 C` 后视觉程序会停止，随后 MCU 应由 100 ms 接收超时进入
`NO_DATA/LOST`。

## 7. 分阶段测试

### A. 只测视觉

- 空管 10 秒：误检数应为 0。
- 左、中、右静态点：检测稳定，符号正确。
- 手动缓慢滚动：无明显掉检和跳变。
- 手动快速滚动：不应从一端瞬间换到另一端目标。
- 轻微晃动支架：记录掉检、候选数、拒绝原因和最大跳变。

重点保存这些状态字段：

```text
time, frames, detected, control_valid, position_mm, velocity_mm_s,
confidence, candidate_count, rejection_reason, rejected_jumps,
detect_rate, data_rate, uart_errors, temperature_c
```

### B. 只测串口

- 连续接收至少 60 秒；
- CRC 错误为 0；
- 序号除线路真实丢包外连续；
- 接收频率约 `59-60 包/秒`；
- 无球时仍持续收到格式正确但 `DETECTED=0` 的包；
- 拔掉 A16 后，MSPM0 在 100 ms 内进入 `NO_DATA/LOST`。

### C. 接入状态机但不接控制

- 先只打印状态迁移、位置、速度和有效性；
- 人工制造短时挡光、移出钢球、拔串口等故障；
- 确认不会把无效位置 0 交给控制器；
- 状态迁移稳定后，再开放控制器输入。

### D. 最后接控制

- 初次联调限制机械角度、速度和电流；
- 记录 MCU 目标、实际电机角度、视觉位置和视觉速度的统一时间轴；
- 先低速小幅测试，再逐级提高，出现视觉跳变立即退出闭环。

## 8. 可以改和不能直接改的内容

可以在有测试证据时修改：

- `confidence_threshold` 和候选框尺寸范围；
- 连续性门限和最大物理速度；
- 最终安装后的 `center_x_px`、`mm_per_pixel`、`position_sign`；
- MCU 状态机的连续有效包数和超时时间。

不能直接修改：

- UART 22 字节布局、CRC 或 flags 含义；
- ROI 尺寸、模型输入尺寸或类别定义，除非同步重训和重新转换模型；
- 相机请求 FPS 提高到 60 以上。实测请求 65 会切入 80 FPS 模式并降低完整循环性能；
- 开启 H.264 后仍声称保持当前 59-60 Hz。该组合尚未完成验收；
- 通过 SSH 再启动第二个 Python 识别进程。相机只能由 launcher 管理的单一进程占用。
